# A9 小程序性能优化计划

2026-11-27 接手复核。此文替代此前未经浏览器验证的提速估算。

## 本轮范围

先修复请求去重、就绪标记和测量工具，再完成固定快照的同条件对照。暂不拆分钱包实现、交易构造、CSS 或缓存构建，不进行候选或生产发布。

- 只合并进行中的只读请求。请求完成或失败立即释放，不缓存业务结果。
- 去重按模式、网络、完整 API 地址、方法、完整 Telegram 认证信息、请求头、超时隔离。认证信息只在内存中参与比较，不写日志或持久化。
- 数据就绪与页面渲染就绪分别记录；旧路由和骨架屏不得触发页面就绪。
- 性能采样独立判断关键 DOM、数据展示、样式和绘制，不依赖新增就绪事件，因此优化前后可用同一测量器。
- 每个场景必须有 5 个有效样本；页面错误、超时、缺失就绪数据不能当作零耗时。

## 测量方法

入口：`a9-mini-app/tests/perf-baseline-v2.mjs`；旧入口转发同一实现。冒烟测试启动本机受控页面，调用正式测量函数，验证人为延迟、超时和页面错误。

统一条件：Chrome headless、390×844、中文亮色、4× CPU 限速、下载 1,250,000 B/s、上传 625,000 B/s、100ms 网络延迟。限速绑定实际被测页的 CDP 会话。

场景：Live 无钱包冷启动、Live 同一浏览器上下文再次打开、Demo 冷启动、四主 Tab 首次进入、模块缓存后切回、合成 Telegram 启动 fragment。最后一项只验证浏览器路由解析，不代表 Telegram 真机或验签。

样本记录 FCP、观测窗口内 LCP/CLS、长任务、首屏可见时间、资源路径/传输量/解码量及切页时间。切页必须等待旧路由容器被替换，避免仅凭 hash 变化宣布完成。跨域 transferSize=0 不能解释为零流量。

## 对照与恢复

工作区包含其他窗口改动，禁止使用全局 stash/pop 采集基线。保留已有 stash，使用仓库外固定副本。基线保留已验收 UI，仅移除本轮请求去重与测量标记；它不是纯 HEAD 500b154。报告记录快照哈希与环境条件。

同一 URL/端口顺序托管前后快照，同一测量器各采 5 次。公网候选只读 API 仍可能波动，需给出范围，不能从一次中位数差异推断因果。Live 再开不等于真实钱包恢复，也不承诺 HTTP 缓存命中。

## 后续优化顺序

1. 依据可信采样确定启动资源的主要成本，再按实际静态依赖拆分非首屏音频或复杂组件。
2. 覆盖率证明收益后再拆页面专属 CSS，必须保证冷切样式先就绪、无闪烁。
3. 验证钱包既有会话恢复、同步 SDK 初始化和签名前门禁后，才考虑进一步拆钱包模块。
4. 最后评估内容指纹及旧 chunk 保留，不给未指纹 JS 直接加永久缓存。

每阶段独立完成同条件复测、全栈基线和浏览器回归。不得预先承诺 20%–30% 提速。真实钱包恢复、iOS/Android Telegram 与慢网断网完整流程单独验收，不能用本轮桌面测量替代。
