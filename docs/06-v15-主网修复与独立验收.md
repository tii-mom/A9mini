# A9mini v15 主网修复与独立验收单

适用基线为 2026-11-21 的 A9mini 工作区。当前结论为暂缓部署。执行模型负责修改和自测，原审查模型负责独立复验，项目方决定是否发布。此次任务授权到方案交接为止。

## 执行边界和交接顺序

遵守根目录 AGENTS.md。所有修改在 A9mini 内，BAM 仅可读取已跟踪的迁移依据。保持四合约架构、标准 Jetton 钱包、现有视觉和 live 只读。保留用户原有改动。工作区根目录没有 Git 元数据，每批开始前记录涉及文件的相对路径、原始 SHA-256、可用的版本标识；交付差异文件或可核对的前后版本。密钥、钱包配置文件及其符号链接目标不得进入交付包。

先执行 A，再确定 B 的两项规格，完成 B 后冻结消息和 getter 格式，再对接 E、F。C 与 D 共用订单和账本结构，先定接口与迁移，再接付款服务。正式域名和部署后才产生的地址允许作为待填项列明。主网广播、生产 D1 写入、资产迁移、Bot/Webhook 切换各需单独授权。测试网广播也应明确所用测试钱包和已有授权，缺少条件时交回待验项。

## A｜立即关闭 live 资金入口

检查 a9-mini-app/js/tonconnect.js、pages/round_hub.js、profile.js、team.js 及预售页面。当前 round_hub 调用普通 TON 转账方法，推广页会请求付款单。页面、订单请求和统一钱包发送入口均执行模式约束。live 可连接钱包和读取数据；所有资金按钮解释只读原因。demo 资金结果只由 demo-data.js 产生，任何模式都不得因钱包已连接而在演示流程弹出签名。审查 api URL 覆盖、Telegram 深链和直接调用入口；生产仅信任部署配置允许的数据源，保留本地开发入口。

验收：使用已连接的钱包替身记录 SDK 调用，遍历质押、预售、凭证领取、推广领取及分享深链；live 的资金订单请求和两种模式的真实钱包交易调用计数均为零。断开钱包、缺 SDK、接口超时后验证提示与重试。刷新和切换模式后检查浏览器存储，不得含余额、订单、凭证、轮次或交易数据。

## B｜合约资金守恒及协议口径

1. 在 RoundController、StakeTicket 和 types 中明确入金、记票、付款、确认每一步的状态、资金所在地址及恢复人。为异步操作分配可持久关联的标识，校验消息来源、所属轮次和所处阶段。处理延迟、重复、旧回执和退回。成功领取必须能证明对应款项完成交付；未证实的付款保持可核对，恢复前先查原单。不能仅凭转账请求已发出或未收到退回确认到账。凭证通知失败时，应可完成原笔记票或退回原笔本金，并保证轮次分母正确。明确待处理入金跨结算边界时的归属。
2. 维持标准 JettonMaster/Wallet。编码前说明标准钱包实际提供的成功信号、发送者、关联字段，以及哪些失败不可由控制器直接观察。给出同一钱包、多个用户、相同用户 queryId 的区分方式。若在现有约束下缺乏可靠信号，提交协议选择和风险给项目方决定，保持合约阻断。对团队发放、销毁和无效入金退款逐一检查同类异步记账问题。
3. 轮号目前使用 uint8。先列明最大可达轮数的证明或扩大轮号的方案；未证明 255 前必然结束时，按扩大轮号实施。同步更新存储、锁仓轮次追踪的 8 位打包、消息、凭证地址推导、getter、索引、前端编码器与运维脚本。明确旧测试网数据读取或版本隔离办法。
4. 15 倍按全轮本金还是按个人本金，需要项目方确认；先分别列出早鸟与普通用户同轮的金额算例。若按全轮，保留并测试现公式；若按个人，先确定封顶余量属于谁、滚存和团队释放怎么算。未经确认保留现口径并标为待决。
5. 用确定性向量检查 15/16/24 个达标时段、价格走廊边界、胜场 5→6 与 10→11、失败销毁、7 天退出、90 天停滞、30 天兜底、奖池与团队池尾差。核对 keeper 结算输入来自完整的 24 个时段，缺失、重复或时间错位数据应阻止结算。保留可重算的源数据与摘要。

验收：Acton 中检查用户和控制器 JettonWallet 实际余额、总供应、凭证和轮次累计值。逐项覆盖记票退回、付款链后段失败、回执延迟或重复、处理中再次领取、跨轮恢复及正常结算。两用户不同权重分别核账，跨 254→255→256 验证旧凭证仍能领取。给出每个故障后恢复到最终状态的断言。最后从干净副本重编译四份产物，比较哈希，解释每份变化后更新基线。

## C｜身份、预测与奖励账本

服务端验证 Telegram initData 签名、有效期与用户身份；钱包绑定验证具有时效和一次性挑战的所有权证明，校验域名、网络及钱包地址。所有影响资金或归属的路由从已验证身份推导用户和收款地址，统一覆盖预测、激活、推广、邀请与预售订单。管理员权限保持独立。预测下单按服务端轮次和截止时间判断；结算和返佣使用唯一业务事件去重。

D1 中以唯一事件标识记录奖励流向。激活扣减、推广入账与成功记录需要一起提交；并发余额更新采用可验证的条件更新或等效机制。保持原始整数精度，注意 100 亿 A9 的最小单位总量超出有符号 64 位整数。实现旧 D1 数据迁移、迁移前后按钱包及全局对账、重复执行迁移的保护。在数据库副本演练。

验收：合法绑定通过；伪造、过期、重复挑战、跨用户、未绑定钱包均拒绝，余额不变。两笔并发入账均保留，同一激活请求多次只成功一次；在扣减和入账之间注入失败，恢复后总额守恒。验证推广服务缺失、重复结算、截止后下注和高精度大额数据。

## D｜生产收款、发币与退款闭环

让 Worker 建立的 D1 订单与实际运行的付款进程共享持久账本。选定一个可部署的签名运行环境，交付启动方式、密钥注入方式和健康检查。去掉 runner 对内存 Map 和同步引擎的依赖。覆盖推广手续费、预售成交、退款、返佣。生产缺 DB、签名端或必要地址时阻止接受新付款单。

入账按网络、真实交易标识、收款人、付款人或订单规则、金额、备注及确认状态核验。保存扫描游标并分页补扫，不能只取最近 30 条或把所有返回记录直接标为 finalized。广播前持久化付款意图，多实例互斥；广播成功仅标为待核实。删除 acton-broadcaster 的时间戳假哈希回退。超时或无法解析结果时先按链上真实记录核对，无法确认则保留人工核对状态。退款和佣金也遵守相同幂等规则。dry-run 使用只读预演。

验收：用与生产相同的 Worker、D1、签名程序，在隔离测试网环境走完推广、成交与退款。提供入账和出账的真实交易标识、收付款钱包前后余额、D1 状态、Gas 和返佣记录。模拟超 30 条积压、两实例并行、入账重复、余额不足、广播后回写前重启、收款人收到 A9 前进程退出、退款暂不可用。最终每笔足额到账或进入可恢复状态，重复扫描不多发。前端保持 live 只读，联调通过独立测试客户端完成。

## E｜真实数据、钱包配置与界面

移除 cf-worker 在未配置地址时返回的初始奖池和轮次。缺值用 null 或规定的错误信封，保留链上真实零余额；逐项核对 data.js 对 BAM ENDPOINTS/ApiResponse 的映射。为个人历史凭证提供完整索引或可遍历的分页，并考虑 RPC 出错、限流、旧轮及未领取权益。行情、24 个时段和倒计时标明数据来源，以服务端时间为准。提供与正式 HTTPS 站点一致的 TON Connect manifest 和可访问图标；禁止发布占位配置。统一 TON、完整数字和中英术语。

验收：测试缺配置、RPC 故障、真实零值、第八轮仍有第一轮待领、浏览器时钟偏差、无行情；区分缺失与真实零值。390×844 及更窄视口检查底栏、弹层、Telegram 安全区、长金额和双语，交付相关截图。清空缓存后验证钱包连接及 manifest 返回内容。

## F｜部署恢复与发布材料

让主网 dry-run 使用与正式部署相同的参数解析和地址推导，检查元数据、网络、权限地址、资金分配、代码哈希和所需余额，列出只可在部署后核实的项目。保留全部广播门禁。部署、铸币、弃权、奖池入账每步核对链上实际状态；已完成且一致可跳过，不一致则停。发现已有合约时校验代码、角色、余额和配置。铸后核对总量 10,000,000,000 A9、管理权状态、控制器初始到账 8,200,000,000 A9 及其余分配。同步更新发布清单，分别记录本地、测试网和待主网核验项。

验收：在隔离环境分别于每一步后中断并重跑，验证无重复铸币或转账。修改一个预期地址或哈希须在广播前失败。对费用提供测试网实测及主网估算依据，余额不足时可停止开轮或接单；提交暂停接单、处理在途订单和对账恢复的操作步骤。
