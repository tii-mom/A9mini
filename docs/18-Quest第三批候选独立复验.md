# Quest 第三批候选独立复验

结论为退回定向修复。验收对象为 release/a9-rc1、d6dd4f0 加当前工作区。交付报告所列八个 SHA-256 均匹配，其中七个前端文件也与本机 18093 实际返回内容逐字节一致。Worker 核算取自本地源码。浏览器资金样例使用隔离的本地接口响应。

## 退修项与关闭条件

1. **P0 金库把急提销毁计入累计已领。** 奖金 1,000 A9，第 0 天一次急提，Worker 签前口径为奖金到账 440、销毁 560。已锁定的 RoundController.tolk 在急提后将 newLockedClaimed 设置为整个锁定额 800，并标记 forfeited。Worker v15-indexer.mjs 将即时已领 200 与该结清值 800 相加，得到 1,000；浏览器切到这张票据也显示累计已领 1,000。修后分别用第 0 天、已部分领取后急提、正常满期领取三种票据核对。若历史到账或销毁无法从票据状态恢复，应取可信结算事件，或在 API 和页面明确返回未知。合约无需调整。
2. **P1 Demo 最后确认时跨过头矿截止仍按 5% 入账。** 在头矿结束前打开最终确认，等待六秒越过截止，以 10,000 A9 确认。账单仍写退 9,500，模拟票据仍写 isFirst6h 为 true。主卡自然跨界已通过。让 Demo 最终操作也依据当前时间、钱包和轮次重新校验；变成普通仓时应展示退 9,000、烧 1,000，并要求重新确认。Live 提交路径已有独立阶段检查。
3. **P1 同一钱包有多笔待发币订单，第一笔结束后其余订单失去跟踪。** 让订单列表有两笔 PAYOUT_SENT，其中第一笔返回 COMPLETED。第一笔到账剧场正常，但随后页面仍有一条“发币已发送 · 等待确认”，等待横幅消失。恢复函数处理完成后停止，未从同一响应继续选下一笔。修后在同一页推进两笔订单，先后完成和反序完成都须按正确订单与金额反馈，每单一次。再测退款、切钱包和离页。
4. **P1 提前解押最终确认仍持有旧票据。** stage-view.js 的最终确认回调只检查钱包、在途锁和当前轮次是否处于锁仓阶段。它没有重读票据权限或确认当前轮次 ID 与旧票据相同。代码核查发现，未开启真实签名。用隔离样例在弹层打开期间改变轮次，或将原票据变为 pending、canEarlyExit=false；最终确认不得调用钱包发送函数。
5. **P1 分享模板仍有虚构阶段或金额的路径。** share.js 的 chest 分支仍为缺失奖励使用 1,000 A9，并在 SHOP_BOOST 的 banter 模板写固定的“12H 冲价正热”。核对生成的每个分享选项，锁仓与冲价阶段分别测试，缺结算金额时省略该金额。只需本地生成文本。
